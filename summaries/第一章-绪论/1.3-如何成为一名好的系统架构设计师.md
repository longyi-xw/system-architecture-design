# 1.3 如何成为一名好的系统架构设计师

> 来源：《系统架构设计师教程（第二版）》· 第 1 章 · 第 3 节（含 1.3.1、1.3.2）

## 一句话概括
先给出衡量一名优秀架构设计师的六个角色特质，再沿「工程师 → 高级工程师 → 技术专家 → 初级 → 中级 → 高级系统架构设计师」的路径说明成长演化。

## 关键要点

### 1.3.1 如何衡量一名优秀的架构设计师

🟡 六条衡量维度（记条目名）：

1. 作为技术领导者
2. 作为开发人员
3. 聚焦系统
4. 具备企业家思维
5. 权衡策略思维与战术思维
6. 良好的沟通

### 1.3.2 从工程师到系统架构设计师的演化

🟡 演化路径（六阶段，顺序须记）：

| 阶段 | 大致年限 ⚠️ | 核心特征 |
| --- | --- | --- |
| 工程师 | 1–3 年 | 可以独立使用框架进行开发 |
| 高级工程师 | 3–5 年 | 在工程师基础上，具备对知识的深度和理论学习 |
| 技术专家 | 4–8 年 | 可以根据需要修改、扩展、优化框架 |
| 初级系统架构设计师 | 5–8 年起 | 大多由技术专家担任；与系统学习过的架构师的区别：缺少从 0 到 1 设计新系统的经验，缺少系统的架构设计方法论 |
| 中级系统架构设计师 | 8–10 年 | 可完成复杂系统的架构设计：高性能、高可用、高扩展、海量存储 |
| 高级系统架构设计师 | 10 年+ | 具备创造性，能创造新的架构模式（如 Docker、MapReduce ⚠️） |

## 我的理解
- 前三个阶段围绕「框架」递进：工程师、高级工程师是**用**框架，技术专家能**改**框架（修改、扩展、优化）。
- 技术专家 ≠ 架构师：差的是「从 0 到 1」设计新系统的经验和系统的架构设计方法论。

## 待核对 · 存疑
- ⚠️ 各阶段「大致年限」与高级阶段的 Docker、MapReduce 例子来自网络资料转述（资料称同出本书），其中技术专家（4–8 vs 5–8 年）、初级架构师（5–8 vs 8 年+）两处年限在不同资料中记载不一致，待翻书核对后去掉此标注。
